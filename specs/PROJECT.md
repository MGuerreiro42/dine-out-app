## Vision

An app for discovering bars and restaurants. Current phase: a navigable prototype to present to business partners, no backend — all data comes from local mocks structured so they can later become a real API without changing components.

## Architecture Principles

1. **Bulletproof-react adapted for React Native.** Every folder in `features/` is an isolated vertical module (`api/`, `components/`, `hooks/`, `stores/`, `types/`). Features NEVER import each other directly.
2. **`src/components/ui/` and `src/components/layout/` are different things.** `ui/` is a generic primitive reused as detail (card, chip, sheet). `layout/` is the structural frame present on (almost) every screen (search bar, side menu). Both live outside `features/` because more than one feature uses them.
3. **State only becomes global when it needs to.** Rule: if only one feature reads/writes a piece of state, it stays in `features/[name]/stores/`. If two or more features need the same state (e.g. "favorited" is read by both `restaurant` and `favorites`), it moves up to `src/stores/` — otherwise the isolation rule (#1) breaks.
4. **Mocks-first with a real network seam, not just an in-memory one.** Every data read in `features/*/api/` goes through a TanStack Query hook whose `queryFn` calls a plain async function in `src/mocks/repository.ts` (was MSW-intercepted `fetch` calls until 2026-08-05 — see ADR log for why that got replaced), backed by the same fixture data that used to be imported directly. Once the real API exists, each repository function's body becomes a real `fetch` call — components, hooks, and the endpoint contracts don't change. Request/response shapes are Zod schemas (`src/types/`, `features/*/types/`) doing double duty as both the TS type and a runtime-checked contract, so a real backend drifting from what the frontend expects fails loudly instead of shipping broken data.
5. **Folder and code naming 100% in English**, including the product name itself (`dine-out-app` — renamed 2026-07-23 from `restaurante-app`, which had been a deliberate Portuguese exception until then; see the ADR log).
6. **Scaffold with the tool's own defaults.** Architecture customization is a separate discussion, not bundled into initial setup.
7. **Don't implement business logic beyond what's explicitly requested.** Placeholder folders (empty `index.ts`) stay empty until a specific feature spec covers that module.

## Tech Stack

| Layer | Choice | Why |
|---|---|---|
| Framework | Expo SDK 57 + Expo Router (file-based) | Current standard for the RN ecosystem |
| Language | TypeScript | — |
| Styling | NativeWind v4 + Tailwind v3 | NativeWind v4 doesn't support Tailwind v4 yet |
| Server state | TanStack Query | Mock→API seam without rewriting components. `staleTime` 5min, `retry` 1 (reduced from the default 3 — a static mock's failures are deterministic bugs, not transient blips; raise it once a real, occasionally-flaky backend exists) |
| Client state | Zustand | Only for genuinely global state (see principle #3) |
| Contracts | Zod | Request/response shapes are schemas, not plain types — `.parse()` on every response catches contract drift immediately instead of silently passing bad data downstream |
| API mocking | Static repository (`src/mocks/repository.ts`) | Plain async functions the query hooks call directly — no `fetch`, no request interception. Was MSW (`msw/native` + `msw/browser`) until 2026-08-05; replaced after MSW's native-runtime quirks (see ADR log) cost most of a session for a mock layer that never actually needed to simulate HTTP. MSW is expected to come back once a real backend exists, for testing *that* backend's real HTTP contract — a legitimately different use case from mocking data that was never going over the wire |
| Testing | Jest (`jest-expo` preset) + React Testing Library | Chosen over Vitest: `vitest-native` (the only way to run RN tests under Vitest) is beta with unconfirmed NativeWind/Expo Router support; `jest-expo` is Expo's own documented path and reuses this project's `babel.config.js` |
| Maps | `react-native-maps` | More performant/scalable than `expo-maps`; accepted trade-off: doesn't run in Expo Go, needs a dev build |
| Import alias | `@/*` → `src/*` | Native to the SDK 57 template via `tsconfig.paths`, no `babel-plugin-module-resolver` needed |

## Folder Structure

```
app/                        # Expo Router routes — thin, delegates to features/
  (tabs)/{index,search,category,profile}.tsx  # 4 real tabs, matching the design's bottom tab bar (Home/Buscar/Categorias/Perfil) — all 4 implemented: index.tsx (US1), search.tsx (US2), category.tsx (US3), profile.tsx (profile.md's US1-2)
  restaurant/[id].tsx
  profile/{orders,reservations,payment,notifications}.tsx  # trivial PlaceholderScreen routes, pushed from the profile tab — real content is profile.md's US3-6
  login.tsx                  # trivial PlaceholderScreen route — real content is auth.md's User Story 1
src/
  components/
    ui/                      # generic primitives (RestaurantCard, BottomSheet, Chip, HorizontalRail, RatingBadge)
    layout/                  # app frame (SearchBar, SideMenu)
  features/
    search/                  # Home + category discovery + search + Search & Map
    restaurant/               # restaurant detail
    favorites/                 # favorites domain (no route of its own — consumed inside profile)
    profile/                   # profile header/stats/account menu (shares the profile route with favorites)
  mocks/                     # fixture data (restaurants.ts etc.) + repository.ts (plain async functions the query hooks call directly — see ADR log)
  stores/                    # global state (favorites.ts, auth.ts, location.ts — see Decisions below)
  lib/                       # queryClient.ts, googlePlaces/ (wire-contract schemas/mappers, see ADR log)
  types/                     # entities shared across features (Restaurant — Zod schema + inferred type)
  theme/, hooks/, utils/     # placeholders, not yet specified
specs/                       # this directory — project and feature specs
jest.config.js
```

## Architectural Decisions (ADR-lite)

<!-- Lightweight record of non-obvious decisions — the "why" that isn't in the code. -->

- **Favorites has no route of its own.** The design (the "Profile" frame) shows favorites only as a rail inside the profile, no dedicated tab. `features/favorites/` still exists as a domain (bulletproof-react separates by domain, not by route) — it just has no `app/(tabs)/favorites.tsx`.
- **"Favorited" state is global, not owned by the `favorites` feature.** The like button also appears in `restaurant` (detail). Under the isolation rule (#1/#3), it can't live only in `features/favorites/stores/` — it moves to `src/stores/favorites.ts`. **Implemented** — ahead of schedule, in `profile.md`'s round (`feat/profile-menu`), because Profile's favorites-count stat needed a real store from day one rather than a `0` placeholder. `favorites.md`'s own User Stories (the like icon, the rail) are still unbuilt.
- **`react-native-maps` instead of `expo-maps`.** `expo-maps` doesn't run on web (the official docs confirm an iOS/Android-only fallback) and is less mature. `react-native-maps` is the market standard, with `react-native-map-clustering` as a companion for scale. Trade-off: needs a dev build, doesn't run in Expo Go — gives real use to the KVM/AVD set up previously on this machine. **Implemented** (`search.md`'s US2, `feat/sidebar-auth`): confirmed `react-native-maps` also has no web renderer at all (not just an Expo Go gap) — solved via a `SearchMapView.web.tsx` sibling file, so Metro's platform-extension resolution swaps in a lightweight placeholder on web and never imports the native module into that bundle.
- **The AVD finally got created (2026-08-06), and native map rendering crashes the whole app without a Google Maps API key.** `MapView`'s mount throws a native `IllegalStateException` ("API key not found") — uncatchable from JS, kills the process outright the instant the Search & Map screen opens. Getting a real key requires enabling billing on the Google Cloud account, currently blocked on that account's own KYC/identity-verification step, not a code issue. Rather than leave the screen crashing, `SearchMapView.tsx` now checks `EXPO_PUBLIC_GOOGLE_MAPS_API_KEY` at runtime and falls back to the same `MapPlaceholder` component web already used (`SearchMapView.web.tsx`'s old inline placeholder, extracted into its own file so both share it) — "O mapa interativo estará disponível em breve." Once a real key exists, it needs (a) `EXPO_PUBLIC_GOOGLE_MAPS_API_KEY` set (flips the fallback off automatically, no code change) and (b) wiring into `app.json`'s `android.config.googleMaps.apiKey` so a rebuilt native `AndroidManifest.xml` actually has it too — that second half is still pending, deliberately not done ahead of having a real key to test it against.
- **`RestaurantCard` was born in `components/ui/`, not in `features/search/`.** `restaurant` also needs it (the "Similar Places" section), and features can't import each other.
- **`RestaurantDetail` extends the shared `Restaurant` type rather than duplicating its fields**, and lives in `src/features/restaurant/types/` (feature-specific), not `src/types/` — the extra detail-screen fields aren't needed by other features, only the base shape is.
- **A spec can drift internally, not just from the code.** Implementing `restaurant.md`'s US1/US2 surfaced that FR-017 and FR-018 were written into the Functional Requirements list without being referenced by any User Story's acceptance scenarios — a spec-authoring gap, not a code bug. Fixed by annotating both FRs in place rather than silently building or silently dropping them. Worth checking for on future specs before implementing, not just after.
- **`msw/node` doesn't work in this project, in the app or in tests — use `msw/native` for both.** MSW's own `package.json` sets its `"./node"` export to `null` under the `"react-native"` resolution condition. `jest-expo` applies that same condition to Jest itself (to accurately emulate what Metro would resolve), so even test-only code hits this. `jest.setup.js` imports the app's own `src/mocks/native.ts` (same `server` instance concept, re-evaluated fresh per Jest process) rather than standing up a separate `msw/node` setup. **Superseded 2026-08-05** — MSW itself is gone, see the "Replaced MSW" entry below.
- **MSW's ESM dependency tree needed explicit Jest config, and that required switching from `package.json`'s `"jest"` key to a real `jest.config.js`.** Two separate misses: (1) `transformIgnorePatterns` needed extending (not replacing — `jest-expo`'s own default already whitelists Expo/RN packages) to also allow `msw`, `@mswjs/*`, `rettime`, and a few of MSW's other transitive deps to be transformed; (2) `rettime` ships `.mjs`, and `jest-expo`'s default `transform` map only covers `.js/.jsx/.ts/.tsx` — needed an explicit `'\\.mjs$'` entry pointing at the same babel-jest transformer. Both require programmatic merging (spreading the preset's own arrays/objects), which a static JSON blob in `package.json` can't do — hence `jest.config.js` requiring `jest-expo/jest-preset` directly. **Partially superseded 2026-08-05** — the MSW-specific allowlist entries and the `.mjs` transform (needed only for `rettime`) were removed; `jest.config.js` itself stays, since the non-MSW `transformIgnorePatterns` entries (RN/Expo packages) are still needed.
- **Expo Router's web target runs in two different JS contexts, and MSW needs to know which one it's in.** The initial request is server-rendered in an actual Node process (`resolver.environment=node` — no `document`, no real network stack), then the client hydrates in a real browser. `msw/browser`'s `setupWorker` throws outside a genuine browser, so `enableMocking()` can't gate on `Platform.OS === 'web'` alone — it also checks `typeof document !== 'undefined'` and skips mocking entirely during the Node/SSR pass (which never resolves queries itself anyway; only the hydrated client does). **Superseded 2026-08-05** — `enableMocking()` is deleted; the static repository has no request-interception step, so this dual-context problem no longer applies to mocking (Expo Router's web target still has two JS contexts, that fact just no longer matters for this).
- **`@testing-library/react-native` v14 made `render` and `renderHook` `async`** (part of its "drops React 18, async APIs by default" migration). Forgetting to `await` them doesn't error clearly — `render()` returns before the component tree mounts, so a synchronous `screen.getByText(...)` right after throws MSW-unrelated-looking `` `render` function has not been called `` from the library's own internals, not from your component.
- **Renamed the product from `restaurante-app` to `dine-out-app`** (2026-07-23) — local directory (`~/Projetos/dine-out-app`), `package.json` name, `app.json` name/scheme/bundle identifiers, GitHub repo (`MGuerreiro42/dine-out-app`) all consistently "dine-out" now. One deliberate exception: `app.json`'s `slug` stays `dine-out-discovery`, not `dine-out-app` — it's already registered against the linked EAS project (`extra.eas.projectId`), and EAS validates the slug on `eas init`/build; changing it locally would just produce a mismatch error without recreating that project, which wasn't judged worth the disruption for an internal-only identifier. The `restaurant`/`Restaurant` naming throughout `features/`, types, and specs is unrelated to this rename — that's the domain entity, always meant to be English regardless of the product's brand name.
- **`isLoggedIn` gets a second global store, `src/stores/auth.ts`, mirroring the `stores/favorites.ts` precedent (ADR above).** The Sidebar Menu (a `components/layout/` concern) needs to conditionally render its header/footer based on login state, and `profile.md`'s "Sair da conta" needs to trigger the same real logout — two independent consumers outside any single feature, same "global if >1 feature needs it" rule that promoted favorites. **Implemented** — ahead of schedule, in `profile.md`'s round: the Profile screen's own header turned out to have the same `isLoggedIn`-conditional layout the Sidebar does (found by re-reading the design's actual frame markup, not just the spec text), so the store was needed immediately, not just for the Sidebar. Default `isLoggedIn: true`, matching the design's own mock — `auth.md`'s own `[NEEDS CLARIFICATION]` about the real first-run default was confirmed to stay open/unresolved (deliberately, not an oversight) when `auth.md`'s own User Stories were implemented. `features/auth/{components}` was scaffolded then too — just the one folder, no `types/`/`api/`/`hooks/`, since `AuthForm.tsx` is the only thing in it and nothing here crosses a wire boundary.
- **`UserProfile` (and its `currentUser` mock) promoted from `features/profile/types/` to shared `src/types/`/`src/mocks/`**, same promotion pattern already used for `Restaurant` (needed by both `search` and `restaurant`). Trigger: the Sidebar Menu, owned by no single feature, needs to read the same current-user data `profile.md` defined to render its logged-in header. **Implemented**, in `profile.md`'s round.
- **New shared `src/components/ui/PlaceholderScreen.tsx`** (back-header + "Em breve" body). `profile.md`'s round needed real navigation targets for 4 account-menu destinations (US3-6, not yet built) plus `auth.md`'s login route — 5 call sites, enough to justify one shared component instead of 5 near-duplicate trivial screens. Each call site gets replaced with real content as its owning spec's User Story is picked up.
- **Logout must be one real action regardless of entry point.** Implementing the Sidebar Menu (`auth.md`) surfaced that `profile.md`'s existing "Sair da conta" (in the account-options list) had been specced as a purely simulated confirmation sheet — a second, different logout behavior from the Sidebar's real one. Corrected `profile.md`'s FR-007 to call the same real `stores/auth.ts` `logout()` instead of leaving two inconsistent logout behaviors on the books.
- **The design added a real bottom tab bar** — an identical 4-item bar (Home, Buscar, Categorias, Perfil) repeated across the "Home", "Category page", and "Profile" frames, only the active item's styling differing between copies. No "Favoritos" tab, consistent with the existing "favorites has no route of its own" ADR above. This resolves a question `search.md` had left open: the `explore` tab (currently an empty placeholder) hosts US2 (Search & Map) only, renamed conceptually to "Buscar" — US3 (Category page) gets its own new "Categorias" tab rather than sharing `explore`, and US3's route turned out to be a fixed tab (`app/(tabs)/category.tsx`), not a dynamic `category/[id]` route as originally guessed. **Implemented** (on `feat/bottom-tab-bar`): `app/(tabs)/_layout.tsx` now has the real 4 tabs (`index`/`search`/`category`/`profile`), `tabBarActiveTintColor`/`tabBarInactiveTintColor` set to `ink`/`muted` matching the design's exact hex values, icons at the time followed the project's emoji-icon convention (no icon library yet — see `search.md`'s Assumptions precedent); **superseded** by the `@expo/vector-icons` migration below, `TAB_ICONS` now holds `IconSpec` values instead of emoji. `search.tsx`/`category.tsx` were trivial placeholders at the time, same as `explore.tsx` was — both later implemented as US2/US3 were picked up, separate work from this tab-bar entry. **Resolved** (previously flagged): the "Search & Map" frame's own markup didn't repeat the tab bar, but the user confirmed it's reached via a normal tab switch ("Buscar" replaces Home) — so it gets the tab bar too, same as the other three; `search.md` updated.
- **The mocked restaurant data contract now mirrors Google Places API (New)** instead of an arbitrary custom shape — `src/lib/googlePlaces/` (`schema.ts`, `client.ts`, `mappers.ts`) holds Zod schemas and helpers checked against Google's current docs (via Context7, not training data): Nearby Search (New) (`POST .../places:searchNearby` → `{places:[...]}`) for the restaurant list, Place Details (New) (`GET .../places/{id}` → a single raw object) for the detail screen, and the real two-hop photo flow (`photos[].name` reference → `GET .../photos/{name}/media` → `photoUri`) instead of shortcutting photos to plain URLs. Why: this project's own principle #4 ("mocks-first with a real network seam") is only as good as how close the mocked contract is to the real one it'll eventually be swapped for — an arbitrary custom shape doesn't actually rehearse that swap.
  - **The wire contract and the internal domain types are deliberately different, on purpose.** `src/types/restaurant.ts`'s `RestaurantSchema` and `src/features/restaurant/types/`'s `RestaurantDetailSchema` are completely unchanged by this — normalization (Google's shape → ours) happens once, inside `useRestaurantsQuery`/`useRestaurantDetailQuery`, so no component anywhere in the app changed. Google's own place `id` is an opaque string; our mock's wire-format `id` is a stringified number purely for our own convenience, converted to a real `number` at that same normalization step — internal routing, the planned `favorites.ts` store (`Set<number>`), and `RESTAURANT_DETAILS`-style lookups all keep using plain numbers, untouched by Google's id scheme.
  - **`occasion`/`ambient`/`menu`/`tags` have no Google equivalent and stay custom** — confirmed with the user rather than force-mapped onto Google's real boolean amenity fields (`goodForGroups`, `liveMusic`, etc.), which would have distorted what those fields actually mean. Our mock's response bundles them as sibling fields alongside the real Google-shaped ones, the same way a real backend-for-frontend layer would enrich a proxied Google response with its own product data.
  - **Gotcha (historical, MSW-only)**: MSW's path matcher treated any `:` in a route pattern as a path-param marker, including Google's own `places:searchNearby` action-suffix convention — needed escaping (`places\\:searchNearby`) in the handler registration or it silently wouldn't match. Moot since 2026-08-05 — `repository.ts`'s functions are named JS functions, not URL route patterns, nothing to escape.
  - **Out of scope, deliberately**: real geo-radius filtering (the mock accepts but ignores the request body's location), `X-Goog-FieldMask`/`X-Goog-Api-Key` headers (real Google requires them; simulating field-mask-based trimming adds mock complexity with no prototype value), and Google's boolean amenity fields for occasion/ambient.
  - **Extended for `restaurant.md`'s US3** (practical info): `regularOpeningHours.weekdayDescriptions`, `internationalPhoneNumber`, and a curated set of Google's real boolean amenity fields now back opening hours, the contact sheet, and the amenities list — same pattern, not a new decision. `whatsapp`/`instagramHandle`/`thingsToKnow` stay custom, same reasoning as `occasion`/`ambient` above.
  - **Extended again for US4** (reviews/highlights): Google's real `reviews[]` (`relativePublishTimeDescription`, `rating`, `text.text`, `authorAttribution.displayName`) backs the Reviews section — an exact field-for-field match, no adaptation needed. `highlights` stays custom. Also surfaced that `userRatingCount` (present since the first Google Places round) had never been mapped anywhere — now backs `RestaurantDetail.reviewCount`.
- **The real navigation Sidebar reuses `BottomSheet.tsx`'s underlying `Modal` technique rather than promoting a new shared `components/ui/` primitive.** `SideMenu.tsx` builds its own left-anchored overlay (`Modal transparent` + backdrop `Pressable` + a stop-propagation content `Pressable`, just `flex-row`/`w-[82%]`/full-height instead of `BottomSheet`'s `justify-end`/rounded-top/bottom-anchored shape) — different enough in edge and sizing that a forced shared abstraction would cost more than the small duplicated `Modal` boilerplate. Animation is a plain fade, matching `BottomSheet`'s own simplified fidelity — no slide/drawer animation library added.
- **A design canvas can contain dangling anchors, not just visible inconsistencies.** The Sidebar's `«` collapse icon links to `#sidebar-collapsed-frame`, an id that doesn't exist anywhere in `App Flow.dc.html` — found by re-reading the frame's actual markup, not just the rendered screenshot. Resolved by treating `«` as a second close-affordance identical to `✕`, not building a distinct "collapsed" sidebar state that the design never actually specifies content for.
- **First real use of `react-native-gesture-handler`/`react-native-reanimated` beyond the mandatory root wrapper** (`search.md`'s US2, the draggable map-results sheet): both were installed but had zero real usage anywhere in the codebase before this. Confirmed against current Reanimated docs (via Context7, not training data) that Reanimated 4's Worklets Babel plugin is auto-included by `babel-preset-expo` since Expo SDK 50 — no `babel.config.js` change was needed. The sheet uses a two-snap-point (collapsed/expanded) `Gesture.Pan()` + `useSharedValue`/`withSpring`, not a continuous free-form drag, and the pan gesture is scoped to the handle/header only — the list content scrolls in its own `ScrollView`, sidestepping the harder drag-vs-scroll gesture handoff for now.
- **Gotcha, found only once the Search & Map screen was actually visible on a device (2026-08-06 — see the AVD entry above): NativeWind `className` silently no-ops when mixed with an explicit `style` prop array on the same `Animated.View`.** `MapResultsSheet.tsx`'s outer `Animated.View` had both `style={[{ height }, animatedStyle]}` (Reanimated's own required pattern) and `className="... bg-white shadow-lg"` on the same element — the `bg-white` never rendered, silently, no warning, leaving the whole sheet transparent (map tiles visible through it) with only the drag handle and count text showing (opaque on their own). No amount of `cssInterop(Animated.View, { className: 'style' })` registration fixes this — that only makes `className` recognized on `Animated.View` at all, it doesn't resolve precedence once a real `style` array is also present. Fix, and the pattern to follow for any future Reanimated component: the animated wrapper carries *only* the animated transform/dimensions via `style`, with zero `className`; all real Tailwind styling (background, radius, shadow, padding) moves to a plain inner `View` with no competing `style` prop.
- **First real use of `react-native-safe-area-context`** (`search.md`'s US2, the floating map search bar): installed since project scaffolding but unused until the Search & Map screen, which is the first screen whose content truly goes edge-to-edge (a full-screen map with absolutely-positioned overlays) rather than scrolling under a normal header.
- **All emoji icons replaced with `@expo/vector-icons`, app-wide.** The earlier "emoji, not `react-native-svg` nor `@expo/vector-icons`" scaffolding-phase decision is superseded — confirmed directly with the user, applied everywhere (tab bar, sidebar, search bars, amenities, ratings, chevrons, category/occasion icons), not scoped to one feature. Chosen over `lucide-react-native` because it needs no native config (fonts via `expo-font`, already a dependency) and works identically on web (this project's `react-native-web` target), unlike `expo-maps`'s earlier web-support rejection. New shared primitives: `src/components/ui/Icon.tsx` (an `IconSpec = { set, name }` resolver across `Ionicons`/`MaterialCommunityIcons`/`MaterialIcons` — icon choices span sets since Ionicons alone lacks several food/amenity glyphs) and `src/components/ui/StarRating.tsx` (a row of star icons, replacing the review section's `'★'.repeat(n)` string trick — the single "★ 4.8"-style rating badges elsewhere stay a single star icon + text, not the full row). Data-driven icons (`Occasion`/`CategorySubtype` in `discoveryTaxonomies.ts`, `AMENITY_RULES` in `useRestaurantDetailQuery.ts`, the redirect-sheet option shape) now store `IconSpec` instead of an emoji string or, for occasions/subtypes, a bare letter (`initial`) — `IconSpec`'s TS union is deliberately stricter than its Zod schema (`z.string()` for `name`) since the real safety net is a compile error at the mock-authoring site, not runtime validation. One accepted exception: `SearchMapView.tsx`'s native `Marker description` is a plain string handed to the platform map SDK's own callout, which can't host a React icon component — the star prefix was dropped from that string instead of left inconsistent.
- **Search bars became real, and the mock grew a second Google-shaped endpoint to support it.** Same day as the item above: `search.md`'s Home/Category/Search & Map search bars were reversed from decorative to a real (debounced) name/cuisine filter, per the user's explicit instruction that this mock layer should be wired the way a real backend integration eventually will be, not a shortcut. Checked current Google Places API docs (Context7): Nearby Search (New) has **no** free-text query support at all — that's genuinely a separate endpoint, Text Search (New) (`places:searchText`, `textQuery` field). Rather than bolt an ad-hoc text param onto the existing `searchNearby` mock (which would misrepresent the real contract, same discipline as the Google Places ADR entries above), added a real `places:searchText` MSW handler alongside it. First uses in this codebase: TanStack Query's `placeholderData: keepPreviousData` (avoids flashing the whole screen's `isLoading` state — which would hide the search bar itself — on every debounced keystroke) and a hand-rolled `useDebouncedValue` hook (no debounce utility existed anywhere before this).
- **`location`/`reviewCount` added to the wire contract and promoted to the core `Restaurant` type**, not kept feature-local (`search.md`'s US2). `location: {latitude, longitude}` is a genuine field on Google's real Place resource that had simply never been modeled before a map screen needed it; `reviewCount` was already on the wire contract (`userRatingCount`) and already consumed by the `restaurant` feature's own detail type, just never read by the search-list mapper. Both are stable, non-contextual facts about a place — unlike `distance`/`tagline`/`tags`/`isOpenNow`, which stay feature-local (viewer-relative or presentational, derived by `useSearchMapDiscovery`, never stored) — so they don't fit the "promote only when presentational needs are shared" reasoning that keeps `DiscoveryCardData`-style fields feature-local.
- **Replaced MSW's network-level mocking with a static in-process repository** (2026-08-05), on the user's explicit call after MSW's native-runtime quirks cost most of a session. Root cause chased down via `adb logcat` on a real EAS-built release APK: `msw/native`'s `setupServer(...).listen()` was throwing `ReferenceError: Property 'MessageEvent' doesn't exist` on Hermes — MSW v2 references `MessageEvent`/`Event`/`EventTarget`/`BroadcastChannel` internally for its WebSocket support, even when only HTTP handlers are registered, and none of the four exist in Hermes. That failure was also silent: `enableMocking()` is fire-and-forget from `app/_layout.tsx` (nothing awaited or caught it), so every screen just failed to load with no visible error — compounded by an earlier, separate bug where `enableMocking()` gated strictly on `__DEV__`, which is always `false` in an EAS release build, so mocking never even attempted to start in that environment at all. Fixing both (a polyfill, then a `try/catch` + `console.error`) got mocking running, but by then the underlying question was why a mock layer that never needs to simulate real HTTP was fighting a native-runtime-emulation problem at all. Decision: `src/mocks/repository.ts` now holds plain `async function`s (`getNearbyPlaces`, `searchPlaces`, `getPlaceDetails`, `getPlacePhotoUrl`, `getDiscoveryTaxonomies`, `getCurrentUser`) that the query hooks call directly — no `fetch`, no request interception, no Hermes-global polyfills, same fixture data as before. `src/lib/apiClient.ts` (the `fetch` wrapper) became fully dead code and was deleted along with it. **This does not abandon principle #4's "real network seam"** — it just moves where that seam sits: a repository function's *signature* (not a URL) is the contract a real backend call will eventually replace, one function body at a time, hook shapes unchanged. **MSW is expected to come back later**, once a real NestJS backend exists — at that point it tests the real backend's actual HTTP contract, a legitimately different (and better-fitted) job than simulating data that was never going over the wire in the first place.
- **Categories Overview (US5) repurposed the existing tab route file instead of adding a new tab** (2026-08-06). Expo Router tabs map `name` 1:1 to a file under `app/(tabs)/`, so there's no way to add a 5th route without a 5th tab. `app/(tabs)/category.tsx`'s tab registration was left untouched; only its content changed, from the per-cuisine page to the new overview grid. The per-cuisine content moved to a new, non-tab `app/category/[cuisine].tsx` — `cuisine` went from an optional query param (`?cuisine=`) to a required path segment, matching `app/restaurant/[id].tsx`'s existing convention, and the screen grew a real back button (same `router.canGoBack() ? router.back() : router.replace(...)` + `chevron-back` pattern already used there) since it's no longer a tab root reachable only by tab-switching.
- **New custom taxonomy `venueType` (`dine-in`/`bar`/`takeout`), backing Home's real Dine-in/Bars/Takeout listing (`search.md` US7, 2026-08-11).** The user proposed reusing the Category page as a generic component for these three icons (previously decorative, `search.md` FR-008); investigation found no per-restaurant data differentiated this axis at all — Google's real `dineIn`/`takeout`/`delivery` booleans (`src/mocks/restaurantDetails.ts`) were hardcoded `true` for all 30 mocks, and no restaurant had a "bar" `primaryType`. Considered reusing those Google booleans directly instead: rejected, because (a) they're non-exclusive (a place can be `dineIn` and `takeout` simultaneously, unlike cuisine's one-value-per-restaurant taxonomy tabs) and (b) "Bars" has no Google boolean equivalent at all. Decision: `venueType` joins `occasion`/`ambient` in the existing "custom product dimension, no Google Places equivalent" bucket (`AppPlaceSchema`/`RestaurantSchema`), not forced onto Google's contract. Assigned to all 30 mock restaurants cyclically by `id % 3` (10 of each) — same "derived, not hand-authored" precedent already used for reviews/amenities in `src/mocks/restaurantDetails.ts`, not a per-restaurant editorial judgment call.
  - **Real-API implementation note, confirmed against Google's current Places API policy (via Context7, not assumed) before committing to this design**: Google's terms prohibit pre-fetching/caching/storing Places API *content* long-term — the only exception is `place_id`, which may be stored indefinitely (`developers.google.com/maps/documentation/places/web-service/policies`). So once this moves off mocks onto a real backend, that backend must **not** persist Google-sourced fields (name, address, rating, photos, hours...) — it persists only `googlePlaceId` + our own product fields (`venueType`, `occasion`, `ambient`), and re-fetches live Google content by `googlePlaceId` on every read, merging the two at request time. This is the real-world version of the `AppPlaceSchema = GooglePlaceSchema.extend({...})` split the mock already models, and dovetails with the existing ADR above that keeps our internal numeric `id` deliberately separate from Google's own place id.
- **The Category page's implementation generalized into a shared `TaxonomyListingScreen` component rather than duplicated for venue-type listings** (`search.md` US7, 2026-08-11) — the same reuse this project had already flagged as likely when `search.md` US6 (Occasion page) was first documented, now built for real. `useCategoryDiscovery` (`features/search/hooks/`) generalized into `useTaxonomyDiscovery`, taking a `dimension: 'cuisine' | 'venueType'` param; `TaxonomyListingScreen` (`features/search/components/`) holds the shared JSX (hero banner, in-page tabs, best-rated/trending/near-you grids), parametrized by a small per-dimension config object (heading wording, fallback back-route) since copy legitimately differs — e.g. no trailing "s" pluralization on venue-type labels, and no subtype row (that's cuisine-only content). Both `app/category/[cuisine].tsx` and the new `app/venue-type/[type].tsx` are now thin route wrappers around it; `CategoryTabsRow`'s `cuisines` prop renamed `items` to match its now-generic role. US6 (Occasion), whenever picked up, should build directly on this pair instead of copying US3's original cuisine-only code.
